## The problem

scikit-learn's `digits` dataset comes from scanned forms: thin, uniform
strokes, no shadow. It's a great teaching dataset for fast iteration, but it
leaves an open question the guided exercise alone doesn't answer: did the
model learn the **concept** of each digit, or just the specific visual style
of that scan?

This project answers that by testing the model on digits it never saw: five
handwritten-digit images generated by AI (Z Image model, via Higgsfield),
explicitly asking for pen strokes on white paper, photo-realistic - unlike
the binarized calligraphy in the original dataset.

> We train a **multiclass classification** model that takes **an 8×8
> grayscale image (64 features)** and produces **the corresponding digit,
> 0 through 9**.

| | |
|---|---|
| **Task type** | Multiclass classification (10 classes) |
| **Model** | `MLPClassifier`, hidden layers (64, 32), ReLU activation |
| **Input `X`** | 64 values from 0 to 16, each pixel's intensity |
| **Output `y`** | An integer from 0 to 9 |
| **Metric** | Accuracy on held-out test set + external image test |

```bash
git clone https://github.com/caiogadotti/reconhecimento-digitos-mlp.git
cd reconhecimento-digitos-mlp
pip install -r requirements.txt
streamlit run dashboard.py
```

The dashboard opens at `http://localhost:8501`, with three tabs: the guided
example (training, loss curve, confusion matrix, comparison with k-NN), the
challenge (the five images, each prediction, and the investigation into why
accuracy drops), and a tab to draw or upload your own digit and see the
live prediction, choosing between the three trained models (original MLP,
augmented MLP, or k-NN).

The original class notebook (`aula04_rede_digitos.ipynb`) has the same
pipeline as a step-by-step exercise, with the challenge's answers written in
the closing section.

## Guided example results

| Model | Test accuracy | Errors (out of 450) |
|---|---:|---:|
| k-NN (k=3, prior assignment) | **98.4%** | 7 |
| Neural network (MLP) | 96.0% | 18 |

k-NN won by a small margin. That's not unusual on small, clean datasets like
this one (1,797 images, 8×8, essentially noise-free): with well-separated
classes in 64 dimensions, looking at the nearest neighbors already solves
most of it, and a neural network's extra capacity doesn't pay off the cost
of training more parameters on so little data.

## The challenge: why does accuracy crash to 20%?

Running the five AI-generated images through the same pipeline gave
**1 correct out of 5 (20.0%)**, including one wrong prediction at 99.7%
confidence. The first hypothesis was preprocessing: the function that crops
and centers the digit uses a **fixed threshold** (`0.2 * image max value`)
to separate stroke from background, and photo-realistic images have shadow
and texture that a simple fixed threshold doesn't isolate well.

Switching to an **Otsu threshold** (adaptive, computes the ideal cutoff per
image) made the crop visually correct - but accuracy **didn't change**,
still 1/5. That ruled out the crop hypothesis and pointed to the real one:
comparing the pixel-intensity histogram of the training dataset against the
challenge images, the distributions clearly differ. In the training set most
pixels sit near 0 or near the maximum value (an almost-binarized scan); in
the challenge images the distribution spreads across the middle of the
scale, an effect of soft shadow and antialiasing from a real photo that
survives the resize down to 8×8.

| | Training dataset | Challenge images |
|---|---:|---:|
| Mean pixel value (0-16) | 4.88 | 4.37 |
| Standard deviation | 6.02 | 4.52 |

The network learned weights tuned to the near-binary contrast of the
training set, and an image with an intermediate distribution falls outside
the region of input space where the model decides with confidence. The
dashboard reproduces this comparison live, with the threshold method
selectable.

---

## Trying to fix it: data augmentation

If the network never saw the real-photo style, the natural next step is
training it on examples of that style. The `augmentar_digito` function
generates copies of each training image with stroke-thickness variation
(dilation or erosion), light blur (`gaussian_filter`, simulating
antialiasing), and noise (simulating shadow and paper texture), and the
network is retrained on the original dataset plus three augmented copies of
each image.

Testing all four combinations (original/augmented network x fixed/Otsu
threshold):

| | Fixed threshold | Otsu threshold |
|---|---:|---:|
| Original network | 1/5 (20%) | 1/5 (20%) |
| Augmented network | 1/5 (20%) | **2/5 (40%)** |

No single fix works on its own: both the crop and the stroke style need
fixing at the same time to see any gain. Even so, 40% is still far from the
original dataset's 96%: the real next step would be training on actual
photos of handwritten digits, with genuine pen-stroke texture instead of a
synthetic approximation of it. Test accuracy on the standard split also
went up with the augmented network, from 96.0% to 98.0%, so augmentation
doesn't hurt performance in the original scenario.
